# GUI dashboard

The client is a Wails v3 desktop app: a Go backend (the packet-capture
client, unchanged in spirit from the old CLI-only version) with a
Svelte frontend rendered in a native webview window, plus a system
tray. There is no `wails build`/CLI tool in the loop - Wails v3 apps
are plain Go binaries. `//go:embed all:frontend/dist` in
`albiondata-client.go` embeds the built frontend, so `frontend/dist`
must exist (via `npm run build`) before `go build` will even compile.

## Backend: internal/dashboard

`internal/dashboard` is the single source of truth for everything the
UI displays. It has no dependency on Wails - it's a plain state-holder
package that the rest of the client calls into:

- `status.go` - `Status` struct (version, update-available, capture
  running/error, server ID, ingest URL, driver warning) plus
  `SetVersionInfo`/`SetCaptureRunning`/etc. setters. Every setter
  follows the same pattern: lock, compute the new value, compare to the
  old one, unlock, and only invoke the registered `OnStatusChange`
  callback if something actually changed. This mutate-emit-if-changed
  shape is deliberate - copy it for any new field rather than inventing
  a different one.
- `counters.go` - per-topic upload counters. `IncrementCounterBy(topic,
  delta)` increments by an actual record count (e.g. `len(orders)`),
  not by 1 per upload pack - counters reflect how much data moved, not
  how many network calls it took.
- `activity.go` - a heartbeat with a staleness timeout. Capture status
  (`CaptureRunning`) is derived from *decoded message activity*, not
  from whether the packet listeners are merely alive - a listener can
  be open and receiving zero relevant traffic. On the
  running-to-stale transition (the edge, not every stale tick),
  counters and the detected server are reset.
- `loghook.go` - a logrus hook that feeds recent log lines to the
  frontend's log tail, capped to a ring buffer.
- `service.go` - `DashboardService`, the Wails-bound struct the
  frontend calls into directly (see
  `frontend/bindings/.../dashboard/`, generated by Wails' binding
  generator - regenerate by running the app in dev mode, don't hand-edit
  except where noted below).

## Frontend: frontend/src

Svelte 5 (runes), Vite. Structure:

- `App.svelte` - top-level layout, owns the design token CSS variables
  (`--bg`, `--amber`, `--font-display`, etc. in its `<style>` block).
  Reuse these tokens for anything new; don't invent colors ad hoc.
- `lib/Sidebar.svelte` - left column: status badge, Server/Version
  fields, resizable width (drag handle, persisted to `localStorage`),
  the driver-warning banner (see windows-capture-pcap.md), counters
  underneath.
- `lib/CountersPanel.svelte` - the counters, as a vertical label/value
  list embedded in the sidebar (not a standalone card grid).
- `lib/LogTail.svelte` - the scrolling log view. UUID-shaped identifiers
  in log lines render as links to
  `albion-online-data.com/identifier?identifier=<uuid>` with a copy
  button.
- `lib/Footer.svelte` - external links (project site, Discord),
  version display. Opened via `Browser.OpenURL`, not in-webview
  navigation - these should open in the user's real browser.

Design direction is "watch-house ledger": dark ink background, a
single amber accent, a serif wordmark used sparingly, monospace for all
data/numerals. This was a deliberate choice (via the `frontend-design`
skill) to avoid generic AI-design defaults. Keep it unless explicitly
asked to redesign.

## Update system: single file, on purpose, on all 3 OSes

The client has never been packaged as a macOS `.app` bundle, a Windows
MSIX, or anything with an installed bundle layout beyond the NSIS
installer's *unpacked* output - it's a bare executable on every
platform. This was reconsidered and explicitly rejected during the GUI
work: the shared updater (`github.com/ao-data/go-githubupdate`,
wrapping `minio/selfupdate`) only knows how to overwrite the single
file it's currently running from. Bundling just macOS would split the
update lineage - existing bare-binary Mac users would need separate
migration logic to ever get a bundle - and break "all 3 platforms use
the same update mechanism" as a property. Windows and Linux don't need
bundling for their own reasons (Windows embeds its icon via
`go-winres` directly into the `.exe` PE resource at build time; Linux
sets window icons at runtime via WM hints). If bundling macOS comes up
again, this tradeoff is why it hasn't happened - it's not an oversight.
One consequence: the macOS Dock icon is known not to work correctly for
the unbundled binary (likely a signing/`Info.plist` quirk), and that's
accepted as the cost of staying unbundled.

See self-update.md for how the updater actually decides what to
download and a real gotcha that comes directly from this single-file,
per-OS-per-arch design.

## Platform-specific pieces

- `internal/console` (Windows only) - hides the console window on
  launch, with a tray toggle to reveal it. `console_other.go` is a
  no-op stub for the other platforms - this Check/no-op-stub split
  (one real implementation behind a build tag, one empty one without
  it) is the pattern to follow for any new OS-specific dashboard
  behavior; `internal/dockicon` and `internal/pcapdriver` use the same
  shape.
- `internal/dockicon` (macOS only) - shows the Dock icon once the
  dashboard window is first shown. Deliberately one-directional: it
  does not hide the icon again when the window is hidden. A bidirectional
  version was tried and reverted - it fought with macOS's
  `NSApplicationActivationPolicy` transitions in a way that made the
  tray icon disappear entirely when a third-party menu bar manager
  (e.g. Bartender) was running. Don't make this bidirectional again
  without a way to test it live against one.
- `internal/winstate` (cross-platform) - window position/size
  persistence to `os.UserConfigDir()/albiondata-client/window.json`,
  debounced 500ms after move/resize.
- Tray double-click (`albiondata-client.go`, `setupTray`) is hand-rolled
  via `tray.OnClick` + a 400ms timer, not `tray.OnDoubleClick`. Wails
  v3's macOS systray backend never wires up a native double-click
  handler (only the Windows backend does - check
  `vendor/.../wails/v3/pkg/application/systemtray_*.go`'s
  `doubleClickHandler` if this ever needs revisiting after a Wails
  upgrade), and a tray icon with a menu attached shows that menu on the
  very first mouse-down when no click handler is registered at all -
  registering `OnClick` suppresses that, then the single/double click
  disambiguation is done by hand.
